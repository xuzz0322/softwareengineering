项目：校园选课系统  
团队组织：常鹂沣 为组长，常鹂沣 同时负责人员管理后端，谭赛 负责鉴权和选课教学后端，吴宪光 负责前端，徐振泽 负责数据库、关闭计费与部署  
报告基线：2026-09-24 的工程快照；业务集成测试更新至 2026-10-13 归档记录

本报告汇总工程目标、职责分工、设计决策、缺陷处理和测试结论，明确当前版本的交付范围与后续验证工作。

## 1. 项目目标与当前结果

项目采用 C++17 后端、HTML/CSS/JavaScript 前端和 MySQL 8.4，实现学生选课与成绩查询、教授授课安排与成绩录入、Registrar 人员管理与关闭选课。课程设计要求的开发计划、需求、设计、测试计划、测试报告及个人/全组总结已分文件整理，可选配置管理计划与源码快照随包提供。

当前演示含 30 门课程、30 个秋季教学班、2 个春季历史教学班、60 名学生、12 名教授及 1 名教务。已有报名与成绩保留；新增学生不预置报名和先修成绩。

## 2. 主要技术决策

业务写入使用 MySQL 事务和同一命名锁保证容量与关课一致性。新草稿不占名额，已提交后的修改草稿保留原报名；提交失败恢复原状态。关闭时先取消无教师班级，按备选顺序补位，再取消不足三人的班级。

权限由后端验证：学生只能修改自己的课表；教授不能修改其他教授的班次；只有所属教授可以录入已结束学期成绩；只有 Registrar 可以维护学生资料。URL 或 JSON 伪造身份、角色均不能授予权限。

最终课表与 outbox 同事务保存，后台持续重试财务投递，接收方使用 event_key 幂等。原题遗留 Ingres 与真实财务没有提供接入条件，当前采用 MySQL 只读目录及本地演示接收端。

## 8. 需求落实与实现过程分析

本项目围绕学生选课形成完整业务流程，而不是分别堆叠三个角色的操作页面。学生提交产生报名，教授认领决定教学班是否具备开班条件，教务关闭会重新整理最终课表，计费又依赖最终结果。任何一处对数据状态的理解不同，都可能使整个流程出现不一致。

需求落实的重点是把数量、时间、身份和状态四类限制转换成服务端规则。数量限制包括四主选两备选、最多十人及最少三人开班；时间限制包括选退课窗口与课程冲突；身份限制包括角色与教学班归属；状态限制包括草稿、正式提交、最终课表和学期关闭。按这几类条件组织检查，有助于覆盖正常流程之外的边界场景。

实现过程中的一个重要修正是明确草稿语义。新建草稿只保存编辑内容，不占用名额；已经提交后的修改草稿不能自动撤销原报名。数据库保留实际报名及上次提交的备选，关闭时据此结算，避免学生尚未确认的修改进入最终计费。需求说明、页面文字、接口和测试都需要表达同一含义。

## 9. 架构方案的收益与代价

C++ 服务同时提供静态前端和 JSON 接口，使本地部署只需访问一个端口，同源请求也减少了跨域配置。MySQL 保存业务记录，后台线程投递计费消息，各部分边界明确，适合课程设计环境中复现和检查。

事务与全局命名锁的选择简化了并发正确性处理。它让报名、教授授课调整、人员维护和关闭选课遵守同一写入顺序，便于分析回滚与互斥。但代价是业务写入串行化：当用户规模增大，等待时间可能成为瓶颈。后续若改为行锁或按教学班加锁，必须同时处理多课程锁顺序、死锁重试和关课屏障，不能只替换一个查询。

财务发送采用持久化消息，避免外部不可用直接阻塞关课。其正确性依赖发送端不丢失消息、接收端按事件键幂等，两端缺一不可。当前演示接收端已验证恢复和重放；真实对接仍需明确认证方式、消息字段、异常响应和对账机制。

## 10. 问题处理中的共性认识

中文乱码和接口字段不一致看似属于不同问题，根源都涉及边界约定。前者是 SQL 文件与数据库连接对字节编码的解释不一致，后者是前端与后端对数据结构的解释不一致。排查时应沿数据流逐层观察实际值，在出现差异的边界修复，而不是在最终显示处加入临时补丁。

数据扩充也说明，修改不能只关注新增行数。新增课程必须有正确先修关系、授课资格和可用时间；新增账号需要完成密码初始化；测试中依赖初始人数和取消班数的预期也要同步调整。通过增量 SQL 保留既有记录，能够让演示环境继续使用，避免为了方便初始化而丢失用户操作。

权限加严进一步体现了“拒绝请求”和“数据保持”需要共同验证。返回 403 并不足以证明安全，如果修改已发生后才报错，仍然构成越权。测试因此保存操作前状态，并在请求被拒绝后重新比较，覆盖课表、教授安排、成绩和人员资料。

## 14. 从需求到交付的完整工作链

全组先把题目拆成可观察的业务行为，再划分职责。学生端的目标是能够查询课程、保存编辑内容并提交有效课表；教授端的目标是维护本人教学班并录入本人班级的已结束学期成绩；教务端的目标是维护人员、关闭选课并查看计费。需求分析特别区分了课程、教学班、课表和实际报名，因为这些概念如果混同，后续的容量、补位及金额都会失去可靠依据。

实现顺序遵循依赖关系：徐振泽 先给出 MySQL 表结构和演示数据，谭赛 建立公共会话、事务和选课教学接口，常鹂沣 在公共鉴权基础上完成人员接口，吴宪光 对照接口契约形成三角色页面，徐振泽 再把正式报名与备选交给关闭计费流程。实际联调不是严格的单向传递；字段、状态或规则出现差异时，需要回到需求说明与数据库结果重新核对。每个岗位的详细工作与交接要求见四份个人总结及分工讲解文档。

交付阶段把“项目能启动”“某场景已测试”“可以对外使用”分开。Compose 健康检查表明服务进程和数据库可用；82 项集成检查表明特定 API 场景通过；完整浏览器操作、压力目标和真实系统联调仍需要独立证据。这个区分直接影响报告措辞，也让后续接手者能据此安排验证。

## 16. 版本变化与问题闭环

项目中有四类值得保留的典型问题。第一类是数据库结构与服务查询不一致，解决方法是沿 SQL 定义和 C++ 查询逐字段对照。第二类是前端假设错误的请求或响应结构，解决方法是更新接口契约并复跑页面状态检查。第三类是中文动态字段乱码，解决方法是从接口返回追到导入连接编码，明确 `utf8mb4`，再谨慎修复已有种子记录。第四类是越权请求虽然有角色限制，却需要更明确的对象归属及拒绝后数据保持检查，因此补齐跨学生、跨教授、成绩和人员操作的边界用例。

每类问题的闭环由五项信息组成：触发输入、错误表现、根因位置、修改点、回归证据。只看到页面恢复不等于数据库值正确；只看到 403 不等于数据未被修改；只看到发送成功不等于不会重复计费。全组测试围绕这些容易误判的环节补充了状态对比与故障恢复场景。

近期又对页面做了展示层优化，统一使用“校园选课系统”名称和蓝色主题，增加筛选、实际报名提示、人员搜索及手机窄屏规则。前端语法与状态检查通过，但没有取得完整的实际浏览器视觉验收记录。视觉改动不改变既有业务测试结论，同时也不能借用 82 项后端结果证明页面细节无问题。

下一轮验收按风险推进：先在真实浏览器完成桌面与手机视口的三角色核心流程，并保存操作记录；再在隔离环境完成备份恢复演练，核对账号、报名、成绩和计费；随后扩大异常和负载场景，记录响应时间、等待、错误率及资源占用；最后按真实外部接口条件进行 Ingres/财务联调。每一阶段都有明确可观察的结果，完成后再更新报告，不以未来计划替代当前证据。

## 19. 全组总结

本项目的主要成果是把课程设计中的角色、选课规则和关课结算连接成可以运行、可以检查的完整流程。常鹂沣 将需求与人员管理落实为接口和验收条件，谭赛 保证身份边界及选课教学事务正确，吴宪光 让三类用户能够通过页面完成操作并理解状态，徐振泽 使数据、结算和部署具备可复现的检查路径。四条工作线通过接口说明、数据库模型、模块测试和交接约定连接起来，单独完成任一页面或接口都不足以构成最终交付。

全组最重要的经验是以数据结果核对业务含义：草稿是否占位、失败后旧报名是否保留、越权拒绝后数据是否不变、关闭后是否按实际报名计费，都需要跨前端、后端和数据库一致地解释。现有自动化结果证明所测业务场景，未完成的浏览器与生产条件验证继续列为后续任务。交付材料保留了实现、测试和限制的对应关系，便于答辩时说明，也便于下一轮按证据继续改进。
