# 常鹂沣 个人工作总结

岗位：组长、需求与人员管理后端  
项目：校园选课系统  
文档范围：对应岗位的模块、技术问题及验证结果

## 1. 岗位职责

本岗位分工覆盖需求理解、进度协调、学生和教授资料增改停用、教师资格维护、人员模块测试及团队文档汇总。报告按成员姓名组织，围绕当前工程说明职责产物和技术结论，不列未经核实的个人工时或贡献比例。

| 题目理解 | 区分课程目录、教学班和个人课表；整理学生、教授、Registrar 三角色的操作边界。 | docs/02-需求分析.md |

## 3. 技术方案分析

本系统最容易混淆的是“关闭选课”和普通选退课：关闭操作需要处理取消、备选补位及最终计费，不能只把学期状态改为 CLOSED。需求说明需要明确新草稿不占名额，而已提交后保存修改草稿保留原报名，避免前端、后端和测试对同一状态产生不同解释。

需求管理采用用例和验收条件双向追踪。相比只罗列功能名称，该方式能明确每项需求由哪个接口实现、用什么检查确认。角色越权必须同时检查响应码和数据库是否变化，不能把按钮不可见作为安全验收依据。

## 4. 问题与处理

| 问题 | 处理及检查方式 |
|---|---|
| 计划与实际不一致 | 采用相对周计划描述依赖，以当前产物状态报告进度；未完成的验收单独安排，避免计划与实测混淆。 |
| 权限验收遗漏 | 用 SEC-01—SEC-04 逐项追踪到后端校验与越权后数据保持测试。 |

项目修复过程体现了定位顺序的重要性：先区分界面、接口和存储层，再通过具体输入与数据库结果验证原因。修复后使用原场景回归，同时检查是否影响已有报名、成绩或账户。

## 5. 验证结果与协作接口

当前版本的 82 项真实 MySQL API 集成检查和 12 项 C++ 规则断言通过；完整记录见测试报告。该结果覆盖权限隔离、输入校验、事务回滚、并发容量、关闭补位和计费可靠性。

协作以需求说明、数据库字段及接口说明为共同约定。吴宪光 处理页面和反馈，常鹂沣 维护人员接口及需求，谭赛 维护鉴权与选课教学事务，徐振泽 维护数据库及关闭计费并汇总回归。各模块负责人对自己的代码和测试一起负责。浏览器完整点击流程与生产性能尚未完成验收，不能计入已通过范围。

## 6. 需求拆解与范围控制

选课系统的需求不能简单拆成“学生页面、教授页面、教务页面”。同一个操作往往跨越多个模块，例如学生提交课表需要读取先修成绩、检查教学班容量、判断时间冲突，并同时写入课表和报名记录。因此，需求整理以业务用例为主线，再确定页面、接口和数据库之间的关系，能够减少各模块分别完成但无法组合运行的问题。

需求中的课程和教学班也需要区分。课程表示名称、学分、费用和先修关系，教学班则表示某学期的具体班次、教师、教室和时间。学生实际选择教学班，但重复判断应落在课程层面，否则可能把同一课程的两个班次同时作为主选与备选。这个区分直接影响数据模型、界面展示和测试输入。

范围控制还涉及原题环境与实际条件。当前没有真实 Ingres 目录和财务系统，所以实现采用只读目录库与本地财务接收端。报告分别说明已实现的适配行为和没有完成的真实联调，不将模拟环境的结果扩大为外部系统已经验收。

## 7. 验收条件的细化

仅写“选课成功”不足以指导验收。正常提交应同时满足四门主选、两门备选、先修通过、时间不冲突和容量未满；提交后数据库应产生四条正式报名。失败场景还要检查原报名是否恢复，不能只检查页面出现错误提示。

权限需求也采用同样方式细化。学生伪造其他学生编号时，接口应拒绝请求，双方课表都不能变化；教授认领他人教学班时，应保留所有原授课关系；学生和 Registrar 不能通过伪造角色录入成绩。这样的条件能让测试发现“响应拒绝但数据已经被修改”的问题。

关课验收则关注完整结果：无教师班级取消、备选按顺位尝试、最终不足三人的班级取消、学费依据最终课程计算。通过把这些结果拆成可比较的数据，可以把需求中的抽象描述转成具体检查。

## 8. 组织衔接与文档一致性

岗位之间的交接以明确产物为中心。需求岗位提供业务规则及异常条件，后端岗位提供接口和错误码，前端岗位核对页面状态与请求格式，数据库测试岗位验证实际写入及回滚结果。任何一方改变字段或规则，都需要检查其余产物是否仍然一致。

本项目曾出现前端期待嵌套课表对象、实际接口直接返回课表，以及成绩请求对象与数组不一致等问题。这说明接口说明需要与实现同步维护，不能在开发前写一次后就不再更新。文档检查应覆盖请求方法、字段名、返回结构、状态码和角色限制。

全组总结还需要区分计划、实现和验收。六周安排属于工作计划，文件存在说明产物已经形成，测试日志说明特定场景已经验证；三者不能互相替代。对未完成的页面验收和生产性能测试单独列项，有助于明确后续工作，而不是用“基本完成”掩盖缺口。

## 9. 人员管理后端与测试责任

人员管理不是仅展示用户列表。请求首先复用 谭赛 维护的会话与角色组件，确认调用者为 Registrar；然后验证姓名、账号、日期及唯一编号。新增学生需检查毕业日期，教师资格必须对应有效课程。编辑人员时不允许改变角色，修改密码后撤销相关会话。

停用人员前检查当前报名和授课关系，有关联则拒绝；停用采用 active=0 并保留历史成绩。常鹂沣 负责新增、修改、停用、重复账号与身份编号、非法日期、资格撤销限制、重置密码及非 Registrar 越权的测试设计和维护。原有已执行检查与新增待覆盖检查要在日志中区分，不能把新分工视为测试已经补齐。

与谭赛 的边界是复用公共鉴权及 Transaction，不自行增加第二套身份机制；与徐振泽 的边界是提出字段需求，由徐振泽 维护 SQL 变更；与吴宪光 的边界是共同确认人员表单字段及错误反馈。

## 10. 阶段认识与后续改进

项目协调的关键是把业务规则转成可核验的接口、数据和测试结果。关课规则、草稿与正式报名的差别，以及谁可以录入成绩，都需要在需求阶段明确。后续验收应优先补齐页面流程和性能证据，避免以功能可用代替完整质量结论。

后续工作按风险排序推进：先完成三角色人工验收和问题复现，再补充边界用例，最后开展性能和故障恢复验证。任何“已修复”结论都应同时说明触发条件、修改位置和验证依据。

## 11. 本岗位的具体工作链路

常鹂沣 首先把题目中的自然语言要求写成可以核对的业务条件。对每个用例至少记录使用角色、前置状态、输入、成功后状态和失败后状态。例如“修改学生信息”并非只检查表单能否保存：调用者必须是 Registrar，学生账号和身份编号不能与现有人员冲突，出生与毕业日期必须有效，修改失败时原资料应保持。需求明确以后，再把条件分别落实到人员接口、前端字段和集成断言。

人员接口的检查顺序应固定：先取得会话身份并校验角色，再读取待操作人员，之后校验输入字段及关联关系，最后在事务中写入。新增教师还要检查所选授课资格是否指向有效课程；编辑时角色和校园账号不能被普通字段修改绕过；停用人员应撤销会话并保留历史成绩。此处与谭赛 的公共鉴权、徐振泽 的表结构和 吴宪光 的人员弹窗都有交接，不能只验证一条成功路径。

作为组长，常鹂沣 还负责把“已实现”“已测到”“尚待人工验收”分开记录。每次接口或规则修改时，先指出受影响的用例和文档，再请对应模块负责人更新实现与测试，最后核对 README、接口说明、测试报告中的字段、数据规模和限制是否一致。这项工作形成的产物是可追踪的规则与验收结论，而不是单纯增加文档字数。

## 12. 协作过程中的检查点

| 阶段 | 常鹂沣 需要确认的内容 | 交给谁、得到什么 |
|---|---|---|
| 需求拆解 | 区分课程、教学班、课表、正式报名和最终计费；列出正常与拒绝条件 | 向谭赛/徐振泽 提供业务顺序，向吴宪光 提供页面状态文字 |
| 人员接口约定 | 必填字段、日期、唯一性、授课资格、停用限制、错误码 | 与吴宪光 对齐表单，与徐振泽 对齐字段和外键，与谭赛 复用鉴权 |
| 模块验收 | Registrar 成功操作及学生/教授越权；拒绝后原记录不变 | 常鹂沣 维护人员用例，徐振泽 执行全量回归并归档结果 |
| 版本收尾 | 文档数字与测试日志一致，说明未验证项 | 汇总四位成员的模块结论和交付材料 |

当联调出现问题时，先记录账号、请求、响应、相关数据的操作前后值，再按接口所属模块分配。不能只依据“前端提示失败”认定是前端问题，也不能因为接口返回 403 就跳过数据不变检查。

## 13. 答辩准备与可讲内容

常鹂沣 适合用一条具体用例串起总体介绍：学生选择具体教学班，后端校验后产生报名，教师负责教学与成绩，教务最后关闭并结算。随后切到人员管理，说明 Registrar 身份检查、字段校验、停用保留历史及对应越权测试。展示代码时定位 `admin/users` 与 `maintain_user`，展示文档时定位需求矩阵和测试报告，不需要逐行解释全部 C++ 服务代码。

交接给吴宪光 前应明确演示账号及学期仍处于开放状态；交接给徐振泽 前应核对现场没有提前关闭选课。若被问及四人工作量，回答以岗位范围和可验收产物说明计划均衡，实际贡献需以组内开发记录确认。若被问及“是否全部完成”，应区分 82 项 MySQL API 检查通过与尚未完成的完整浏览器、性能和真实外部系统验收。
