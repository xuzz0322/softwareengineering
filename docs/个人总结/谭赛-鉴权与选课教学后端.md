# 谭赛 个人工作总结

岗位：鉴权与选课教学后端  
项目：校园选课系统  
文档范围：对应岗位的模块、技术问题及验证结果

## 1. 岗位职责

本岗位分工覆盖会话鉴权、选课事务、授课安排、名册、成绩、公共事务组件及对应规则和并发测试。人员管理由常鹂沣 主责，关闭补位及计费由徐振泽 主责。报告按成员姓名组织，围绕当前工程说明职责产物和技术结论，不列未经核实的个人工时或贡献比例。

## 2. 模块与产物

| 工作项 | 主要内容 | 对应文件 |
|---|---|---|
| HTTP 与权限 | 核验会话、CSRF、角色和对象归属，接口不能信任请求中的角色或用户编号。 | backend/src/service.cpp |
| 业务与事务 | 检查先修、冲突、容量、回滚及关课顺序，保证写入原子性。 | backend/include/domain.hpp、backend/src/db.cpp |
| 教学与规则测试 | 核验本人名册、成绩归属、先修、冲突、容量、失败回滚及并发。 | backend/src/service.cpp、tests/domain_tests.cpp、tests/integration.py |

相关接口或数据规则发生变更时，需要同步代码、需求追踪和测试预期。产物验收以可运行行为与文件内容为依据。

## 3. 技术方案分析

课表写操作以会话用户 ID 作为数据库条件。普通写请求取得同一 MySQL 命名锁后开始事务；提交时暂时移除本人旧报名，再校验和重建，任一步失败都回滚。关闭操作以零等待取得同一锁，因此存在正在进行的报名事务时会拒绝关闭。

采用服务端会话作为身份来源，并在每条写路径执行角色和对象归属检查。相比依赖客户端传入编号，该方式避免跨学生、跨教授操作。数据库全局命名锁实现简单、跨进程有效，代价是写入串行化；当前选择优先保证课程设计规模下的正确性。

## 4. 问题与处理

| 问题 | 处理及检查方式 |
|---|---|
| 跨学生课表操作 | 检查 URL 和 JSON 中的 student_id；他人编号返回 403，并核验双方课表不变。 |
| 跨教授成绩操作 | 同时校验 PROFESSOR 角色、班级所有权、学期已结束和学生在名册内。 |

项目修复过程体现了定位顺序的重要性：先区分界面、接口和存储层，再通过具体输入与数据库结果验证原因。修复后使用原场景回归，同时检查是否影响已有报名、成绩或账户。

## 5. 验证结果与协作接口

当前版本的 82 项真实 MySQL API 集成检查和 12 项 C++ 规则断言通过；完整记录见测试报告。该结果覆盖权限隔离、输入校验、事务回滚、并发容量、关闭补位和计费可靠性。

协作以需求说明、数据库字段及接口说明为共同约定。吴宪光 处理页面和反馈，常鹂沣 维护人员接口及需求，谭赛 维护鉴权与选课教学事务，徐振泽 维护数据库及关闭计费并汇总回归。各模块负责人对自己的代码和测试一起负责。浏览器完整点击流程与生产性能尚未完成验收，不能计入已通过范围。

## 6. 事务设计与异常路径分析

修改课表时，如果先删除旧报名并立即提交，再检查新课程，就可能在校验失败后让学生失去原有名额。当前实现把删除旧报名、读取最新人数、校验新选择和写入新报名放在同一事务内。只有全部步骤成功才提交；发生业务异常或数据库异常时回滚，从而保持操作前后的完整状态。

暂时移除本人旧报名还有一个实际原因：学生重新提交包含原课程的课表时，不能把自己原先占用的席位当作他人名额。事务内重新计算人数，能够正确处理“班级已满但学生原本就在班内”的情况。这个处理必须与回滚结合，单独删除原记录会引入数据丢失风险。

并发控制不能只依赖前端按钮禁用。两个请求可能同时看到最后一个空位，因此容量检查和写入必须处在同一受控范围。MySQL 命名锁让不同服务进程遵守同一个写入顺序；最新测试中十二名学生提交相同的四班组合，前三班各剩五席，最终五人成功、七人被拒绝。该结果验证了所测场景的容量约束，但不证明高并发性能目标已经达到。

## 7. 角色权限与对象权限

角色校验回答“这个身份能否调用此类功能”，对象校验回答“能否操作这一条具体数据”。成绩接口需要先判断调用者是教授，再判断教学班是否由该教授负责。仅完成第一步仍会允许教授修改他人班级成绩。

课表接口始终使用会话用户编号作为查询和写入条件。对于请求中明确指定其他学生编号的情况，增加显式拒绝，使错误反馈与访问边界一致。人员接口则只允许 Registrar 操作，即使学生修改自己的资料也不能绕过这一规则。客户端提交的 role 或 professor_id 不能改变服务器识别的身份。

批量成绩保存同样需要原子性。每条成绩都要验证等级以及学生是否在班内，任何一条失败都应回滚整批修改，避免部分学生成绩更新、部分学生失败后前端难以判断状态。

## 8. 与徐振泽 的关课计费交接

关课算法与财务投递由徐振泽 主责，谭赛 负责确认报名数据、锁与事务交接，并进行交叉评审。关课算法包含两个容易混淆的阶段：取消无教师班级，以及最终取消人数不足的班级。有教师但暂时不足三人的班级仍可能通过备选补位达到开班人数，因此不能在补位之前一律移除。当前实现先处理无教师班级，再按学生编号与备选顺位补位，最后统一检查最低人数。

计费不直接放在数据库事务中等待外部 HTTP 成功。否则财务服务长时间不可用会占用事务和业务锁。当前事务只保证最终课表与 outbox 消息同时保存，后台线程负责发送；这样财务失败不会撤销已经完成的关课结果，也不会丢失发送任务。

如果接收端已经记账，但发送端未收到成功响应，重试可能重复投递。event_key 将同一学生同一学期的结算识别为同一事件，接收端据此避免重复记录。后续真正对接财务系统时，双方必须明确这一协议，不能只在发送端认为“已经做了重试”就认为可靠性问题全部解决。

## 9. 阶段认识与后续改进

关课先取消无教师班级，再按学生编号和备选顺位补位，最后取消不足三人的班级。最终课表与计费消息在同一事务中保存；后台线程投递失败后保留消息，接收方依靠 event_key 防止重复入账。当前全局写锁保证演示确定性，但不能据此承诺大规模性能。

后续工作按风险排序推进：先完成三角色人工验收和问题复现，再补充边界用例，最后开展性能和故障恢复验证。任何“已修复”结论都应同时说明触发条件、修改位置和验证依据。

## 10. 从请求到提交的实现链路

谭赛 的工作可按一次课表提交解释。请求进入服务后读取 HttpOnly Cookie 对应的会话，核验 CSRF 和 STUDENT 角色，课表所有者只从会话取值。再检查当前学期是否允许修改、主选和备选数量、课程重复、先修、时间冲突及教学班人数。取得统一写锁并进入事务后，临时移除本人旧报名，按数据库中的最新人数重算容量，写入新课表和报名；任何一步异常都回滚。提交成功才表示名额真正占用，浏览页面和保存新草稿都不能当作成功报名。

授课安排以 PROFESSOR 身份、课程资格和教学时间为条件。已有其他教授的班级不能直接改归属；名册查询和成绩修改还必须核对教学班归属。成绩录入只针对已结束学期，学生必须在该班名册内，批量保存中有一条非法成绩也不应留下局部更新。这些检查需要在路由入口和对象读取之后分别完成，避免只做角色判断。

公共 Transaction 和数据库命名锁为选课与关课提供同一协调机制。谭赛 与徐振泽 的交接重点是：徐振泽 读取的是实际报名及上次提交的备选，不是学生正在编辑的草稿；徐振泽 的关闭请求需要与普通选课互斥。此约定一旦改变，必须同时重审 谭赛 的课表保存、徐振泽 的补位结果及 吴宪光 的状态提示。

## 11. 测试责任与缺陷定位

谭赛 的测试不能只提交一份合法课表，还要构造缺先修、同一课程两个班、时间冲突、人数已满、学期关闭和跨学生伪造编号等场景。对每个失败请求，检查 HTTP 结果以及旧报名、备选顺位和课程人数是否保持；对并发抢位，直接核对数据库中每班人数不超过十。成绩侧同时覆盖学生、教务及其他教授拒绝，以及本人合法录入和批量错误回滚。

鉴权问题排查从会话及角色开始，业务冲突从入参和学期状态开始，人数异常从事务与锁顺序开始。测试日志中的 82 项是全组集成结果，并非 谭赛 一人完成的测试数量；谭赛 对自己维护的权限、选课、教学和成绩用例负责，徐振泽 负责组织全量执行。出现回归失败时，谭赛 给出最小复现请求、预期数据变化和修复后针对性验证，再交 徐振泽 复跑受影响流程。

## 12. 答辩说明与技术取舍

讲解时建议选两段代码：一段是会话身份与归属判断，一段是课表提交事务。先回答“为什么前端不能决定权限”，再解释“为什么校验和写入必须处在同一受控事务”。教授流程用名册和已结束学期成绩说明对象权限，避免把“教授角色”误说成可以录入所有班级成绩。

全局命名锁简化了跨进程容量竞争与关课互斥，但会串行化写请求。它适合目前课程设计的正确性演示；原题的大规模并发目标没有由十二人竞争测试证明。后续优化需要在保持容量正确、关课屏障和失败回滚的前提下考虑更细的锁与连接管理，不能只为了提高吞吐而删去锁。
