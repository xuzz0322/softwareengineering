## 3. 技术方案分析

数据库把只读课程目录放在 legacy_catalog，将报名、课表、会话、计费和审计放在 registration。enrollments 使用学生和教学班联合主键，schedules 使用学生和学期联合主键；计费对学生和学期唯一，避免关闭重复收费。

数据库使用关系表维护正式报名，用 JSON 保存主选和备选顺位，金额按整数分存储。测试与演示分别使用独立 Compose 项目和数据卷，避免回归测试污染演示状态；配置快照排除密码和数据库备份。

## 6. 数据模型与业务约束

数据库设计需要同时考虑当前操作和历史数据。课程目录记录相对稳定的课程信息，教学班记录某个学期的具体安排；报名表连接学生和教学班，课表表保存主选及备选顺位。将这些概念分开，可以避免修改某个班次时意外改变课程基本信息。

正式报名与编辑草稿不能混用同一字段表达。enrollments 是实际占位依据，schedules 保存编辑选择及上次提交的备选。关闭时依据真实报名结算，能够保证保存修改草稿不会撤回原正式课表。相应测试同时检查报名条数和备选顺位，而不是只读取页面状态。

人员删除采用停用方式，保留历史报名和成绩，同时撤销会话。这样能够维护历史查询所需的关联信息。计费记录保存独立事件与金额，也不应随着人员资料调整而消失。数据模型的完整性不仅表现为当前查询成功，还包括历史记录在后续修改后仍能解释。

## 7. 中文编码与增量维护

中文编码修复首先要区分客户端连接编码与表字符集。即使表使用 utf8mb4，如果导入连接将原始字节当作 Latin-1 解读，错误内容仍会被正常保存。初始化 SQL 因此显式设置 SET NAMES utf8mb4，使输入字节按正确编码解释。

已有数据的处理采用先备份、再精确匹配错误种子值的方式，避免全表转换覆盖后来输入的正常中文。修复后核对课程、学院、教室、姓名及学期字段，并将这些内容加入新库初始化测试。这样既处理当前故障，也减少以后重新部署时复发的可能。

扩充到三十门课程、六十名学生和十二名教授时，使用新增 SQL 文件保留原账号、选课和成绩。新增教授需要匹配授课资格与教学班，新增学生不随意生成先修成绩。数据量增加只是一个目标，关系正确、编码正确以及原业务不受影响同样重要。

## 8. 测试设计与结果解释

测试设计优先验证业务结果及数据不变性。例如，越权请求应返回拒绝，同时比较目标记录和关联记录是否保持；非法课表提交应保留旧报名；并发测试应直接统计 MySQL 人数，不能只统计接口成功数量。响应和数据库两层证据结合，才能提高结论可信度。

并发用例临时创建十二个账号，每人提交相同的四个班；其中前三个班各剩五席，因此五人成功、七人被拒绝。检查还直接核对各班人数不超过十。测试结束清理临时账号和报名，再继续运行关闭及计费场景，避免前一个场景的数据影响后一个场景。

计费测试模拟接收端不可用、恢复可用以及成功消息重放，分别检查待发送状态、最终送达和接收记录数量。这里验证的是演示接收端的协议行为，不涉及真实付款，也不代表已经完成外部财务联调。

## 9. 部署与配置管理

Compose 将应用与数据库分开运行，通过健康检查确定启动状态。网页绑定本机回环地址 8080，数据库为本机 Navicat 使用仅映射到 127.0.0.1:3307，均不向局域网开放。项目配置中的数据库密码和财务密钥保存在本地环境文件，源码压缩包排除这些内容，避免把个人运行环境直接复制给其他人。

配置库归档不仅包含代码，还需要 SQL、测试、依赖许可证和运行说明。SHA-256 清单用于核对解压文件与归档内容是否一致，但文件摘要不能替代业务验收，也不能代表存在完整 Git 协作历史。后续还应在隔离环境执行完整恢复演练，检查账户、报名、成绩和计费状态能否共同恢复。

## 10. 关闭补位与计费模块责任

徐振泽 主责 domain::level、关闭注册接口、计费查询和重试接口、billing_loop 及演示接收端。关闭流程复用 谭赛 的公共事务组件，按正式报名读取主选及上次提交的备选；先取消无教师班级，再补位，最后取消不足三人的班级。最终报名、学期状态和 outbox 必须同事务保存。

投递失败后保留记录并退避重试，接收端按 event_key 去重。徐振泽 维护补位顺序、最终人数、学费金额、关闭互斥、故障恢复与重放测试；谭赛 主责普通选课并发容量，常鹂沣 主责人员模块，吴宪光 主责页面验收。徐振泽 执行完整回归并将缺陷交回模块负责人，避免结算编码与全组测试编写同时集中在一个人。

## 11. 阶段认识与后续改进

初始化 SQL 明确 SET NAMES utf8mb4，避免客户端按 Latin-1 解释中文。测试脚本创建 course-registration-tests 独立项目，使用 18080/13307 端口，结束时只删除该测试卷。并发用例让十二名学生提交相同四班，其中前三班各剩五席，预期五成功、七冲突，数据库人数不超过十。

后续工作按风险排序推进：先完成三角色人工验收和问题复现，再补充边界用例，最后开展性能和故障恢复验证。任何“已修复”结论都应同时说明触发条件、修改位置和验证依据。

## 12. 数据与结算的工作链路

徐振泽 的工作从数据模型开始。只读 `legacy_catalog.courses` 提供课程信息；`registration` 保存学期、人员、教学班、资格、课表、报名、会话、计费消息和审计。课程与班次分开，才能让同一课程有不同学期、教师和时间；课表与报名分开，才能表达编辑草稿和实际占座的差别。徐振泽 维护 SQL 结构、种子数据和增量扩充，同时核对 C++ 查询字段与数据库定义一致。

关闭选课时读取正式报名与上次提交的备选，先取消无教师教学班，再按学生及备选顺位尝试补位，最后取消仍不足三人的班级。结果包含最终报名、学期关闭状态和每位应计费学生的 outbox 记录，这些必须在同一事务中落库。后台发送失败时保留待发送消息并按退避策略重试；接收端使用 `event_key` 判断重复投递。这样“关课成功”“消息已送达”和“真实付款完成”是三个不同结论，本项目只验证前两项的演示行为。

部署链路为本地 `.env`、Compose 应用与 MySQL 容器、健康检查和 8080 本机网页。测试使用 `course-registration-tests` 独立项目、独立卷与 18080 端口，避免脚本重置演示数据。普通停止不删除卷；只有明确需要重建测试环境时才清理测试项目数据。交付源码包不包含本地密钥、数据库卷或备份。
