# 谭赛 分工合作与讲解指南

岗位：鉴权与选课教学后端。重点说明请求进入后端后如何鉴权、如何保持数据一致，以及失败时为什么不会留下部分修改。建议讲解约 4 分钟。

## 1. 负责什么

负责公共会话鉴权、课表提交、教授授课、名册、成绩、公共事务，以及本模块规则和并发测试。人员接口由常鹂沣 负责，关闭补位和计费由徐振泽 负责。需要解释核心代码的因果关系，不必逐行讲第三方 HTTP 或 JSON 库。

| 文件或定位关键词 | 必须能讲清的内容 |
|---|---|
| backend/src/main.cpp | 服务启动、静态页面、HTTP 线程池和计费线程 |
| service.cpp 的 authenticate、role、require_own_schedule | 会话身份、CSRF、角色和课表归属 |
| service.cpp 的 PUT /api/schedule | 校验、旧报名移除、重建和事务提交 |
| backend/src/db.cpp 的 Transaction | 命名锁、提交、析构回滚 |
| backend/include/domain.hpp 的 conflicts、passed、can_add | 先修、冲突和容量；level 由徐振泽 主讲 |
| service.cpp 的 grades 路由 | 成绩角色、归属、学期和名册检查；billing_loop 由徐振泽 主讲 |

用函数名搜索定位，避免依赖后续编辑可能变化的行号。

## 2. 协作交接

与常鹂沣 确认业务规则的唯一解释，尤其是最低人数在补位之后判断、修改草稿保留原报名。与吴宪光 约定 PUT/POST 方法、JSON 字段、状态码及页面反馈；不能只给一个接口地址。与徐振泽 确认字段、报名快照、关课复用的事务边界及演示数据。谭赛 自行维护选课并发、鉴权、授课及成绩测试，徐振泽 只负责组织全量回归。

字段变更后，应通知 吴宪光 修改读取方式，通知 徐振泽 更新真实数据库测试，再同步 docs/09-接口说明.md。权限修改必须测试其他角色请求和原数据是否保持。

## 3. 推荐现场演示

承接 吴宪光 已提交的学生课表后，使用 prof01 登录，初始演示密码为 Campus2026!；若本地已改密码，使用实际密码。

1. 打开“我的教学班”，展示本人班级和学生名单，解释不能查看他班名册。
2. 打开“成绩录入”，选择春季“程序设计基础”，说明只有已结束学期可录入。
3. 如需演示修改，将 student01 的成绩改为 A 或 B 并保存；两者均通过先修，不影响后续关课。不要改成 F/I 破坏预设案例。
4. 切到代码，讲身份来源与成绩路由的教授、归属、学期、名册四层检查。
5. 再讲课表事务和先修、冲突、容量规则，把关课算法、计费代码和最终操作交给徐振泽。

本学期授课认领可展示页面及归属限制，主流程演示中不要随意取消原教授分配，否则会改变后续关课结果。越权结果可以展示已有测试日志，不必临时在现场手写攻击请求。

## 4. 核心讲解内容

**课表事务。** 先取得统一写锁，在事务内移除本人旧报名，再按最新人数检查新选择并重建报名。失败会回滚，因此既不会丢失原课程，也能避免把自己原占的座位当作他人占用。

**权限。** 数据库读取的会话角色才可信。学生带其他 student_id 返回 403，实际查询仍绑定当前会话；成绩接口不是“只要是教授就可以”，还必须是这个班的教授。Registrar 可以维护学生资料，但不能录入成绩。

以下为对 徐振泽 模块的交接背景，现场只需一句带过，由徐振泽 展开代码与演示。

**关课顺序。** 取消无教师班级，按顺位补位，最终再取消不足三人的班级。有教师的临时小班可能通过补位达到三人，所以不能一开始全部取消。

**可靠计费。** 最终课表和 outbox 同事务保存，后台投递失败后继续重试；接收端按 event_key 幂等。关课成功与财务已送达是不同状态。

## 5. 注意事项

- 主选数量、先修、时间冲突和容量都由后端最终校验，不能归功于按钮禁用。
- 跨教授认领已有教师的班级返回 409；名册或成绩越权返回 403，不要混说。
- 无效成绩为 400；前端留空项会被省略，不是后端接受空字符串。
- 全局命名锁保证所测并发正确性，但写入串行化，不能宣称满足 2000 并发。
- 不要为讲解直接改 SQL 或放宽权限；使用已准备的演示账号和测试证据。
- 程序按实际报名关课，不是简单筛选 status=SUBMITTED；修改草稿也可能保留正式报名。

## 6. 常见追问与回答

**为什么要临时删除旧报名？** 重算容量时扣除本人原报名，避免原课程已满导致自己无法保留。删除和新写入同事务，失败会恢复。

**事务能否单独解决超额？** 不能只依赖“用了事务”这个事实。并发请求仍可能读到相同余量；当前命名锁把检查与写入串行化。

**发送成功后响应丢失怎么办？** 发送端可能重试，接收端使用同一事件键避免重复记账。

**四门主选最后是否仍有四门？** 不保证。备选可能不满足条件，最终不足三人的班也会取消；最终课表可少于四门。

## 8. 讲解中的因果链与检查清单

从“student01 提交课表”切入，比逐个报函数名更容易讲清后端：会话确认本人 → 学期和数量检查 → 先修、重复课程与时间检查 → 加锁并在事务内重新计算容量 → 保存报名或完整回滚。可以指向 `PUT /api/schedule` 中相应逻辑，再用已归档的并发与失败回滚断言证明所述行为。

教授部分再用一个反例说明对象归属：另一教授即使拥有 PROFESSOR 角色，也不能修改本班名单或成绩；当前教授还只能给已结束学期、在本人教学班名册中的学生录入成绩。若现场演示本人评分，保存后由学生成绩页复核，随后把“结算读取正式报名”的话题交给徐振泽。

上场前确认测试日志、教学班归属和历史学期状态；不要为证明越权而临时改数据库。被问及大规模并发时，说明目前验证的是正确性场景，全局写锁带来串行化代价，尚无原题 500/2000 并发性能证据。
